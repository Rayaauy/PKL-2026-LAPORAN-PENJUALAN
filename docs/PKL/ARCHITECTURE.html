Architecture

System design and request flow

MVC Pattern

HTTP Request ↓ routes/web.php (Route matching) ↓ Middleware (Auth check, rate limit) ↓ Controller (Request handling + validation) ↓ Model (Database queries) ↓ Database (MySQL/MariaDB) ↓ Model returns data ↓ View (Blade template rendering) ↓ HTTP Response (HTML to browser)

Request Flow Example

Creating a Product

1. User submits form
   POST /products

2. Route matches
   Route::post('/products', [ProductController::class, 'store'])

3. Middleware checks
   - auth: User logged in?
   - throttle: Rate limit OK?

4. Controller processes
   ProductController::store()
   - Validate input
   - Get auth user
   - Create Product model
   - Save to database

5. Model relationships
   Product belongsTo User
   Product belongsTo Category
   Product hasMany TransactionItems

6. Response
   Redirect /products with success message

Authentication Flow

Login form submission ↓ LoginController::login() ↓ Hash(password) == users.password in DB? ↓ Session created Store user_id in session/cookie ↓ Redirect to dashboard ↓ Session persists on every request Logout clears session

Authorization

Two levels of access control:

Middleware-based (route level)

Route::middleware('auth')...       // Requires login
Route::middleware('admin')...      // Requires is_admin=true
Route::middleware('throttle:60,1') // Rate limit

Model-based (resource level)

// In controller - check user ownership
$product = Product::find($id);
if ($product->user_id !== auth()->id()) {
    abort(403);  // User doesn't own this resource
}

Every resource is scoped to the authenticated user. User A cannot access User B's data.

Data Isolation

All queries include user_id filter:

// Products
$products = Product::where('user_id', auth()->id())->get();

// Transactions
$transactions = Transaction::where('user_id', auth()->id())->get();

// Reports
$revenue = Transaction::where('user_id', auth()->id())->sum('total_amount');

Database Relationships

User (1) ├──1:1──> BusinessProfile ├──1:N──> Category ├──1:N──> Product │ └──1:N──> TransactionItem └──1:N──> Transaction └──1:N──> TransactionItem └──M:N──> Product BlogPost (standalone)

Cascade Behavior

ON DELETE CASCADE

If user deleted:

  • All categories deleted
  • All products deleted
  • All transactions deleted
  • All items deleted

ON DELETE SET NULL

If category deleted:

  • Products.category_id → NULL
  • Product remains (not deleted)

ON DELETE RESTRICT

If product in transaction:

  • Delete blocked
  • Prevents data loss

Controller Pattern

RESTful convention followed across all controllers:

Action HTTP Method Route Controller Method
List all GET /products index()
Show form GET /products/create create()
Save POST /products store()
Edit form GET /products/{id}/edit edit()
Update PUT /products/{id} update()
Delete DELETE /products/{id} destroy()

File Organization

Location Purpose
app/Http/Controllers/ Request handlers (RESTful pattern)
app/Models/ Database models with relationships
app/Http/Middleware/ Request interceptors (auth, admin checks)
resources/views/ Blade templates (layout + features)

Error Handling

Validation Errors

    'name' => 'required|string|max:255',
    'price' => 'required|numeric|min:0',
]);
// Returns 422 with error messages if invalid

Authorization Errors

abort(403);  // Forbidden (user not owner)
abort(404);  // Not Found (resource doesn't exist)

Performance

Eager Loading

// Bad: N+1 queries
$products = Product::all();
foreach ($products as $p) echo $p->category->name;

// Good: 2 queries
$products = Product::with('category')->get();

Query Optimization

  • Foreign keys indexed automatically
  • Select only needed columns
  • Pagination on large lists
  • Cache expensive queries

Deployment

  • Set APP_ENV=production
  • Set APP_DEBUG=false
  • Configure HTTPS/SSL
  • Run php artisan migrate
  • Setup automated backups
  • Monitor error logs
